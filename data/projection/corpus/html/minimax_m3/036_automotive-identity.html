Vehicle-Identity Attestation Pipeline — Library Upgrade Forged 7,312 Records With Bypassed Signature Counter

A two-fault composition in vin-canonicalizer (parser upgrade) and attestation-issuer (fallback path without invariant) caused signed vehicle-identity attestations to be emitted with sig_counter = 0 over a 47-minute window. All 7,312 affected attestations were revoked and re-issued; 12 B2B merchant tenants in dealer-finance and fleet-lease verticals were impacted; no PII, no driver-licence data, no payment credentials were exposed. Customer credits in the form of SLA-breach waivers were issued under incident-2024-Q3 credit policy.

Narrative #root-cause-narrative

On Wednesday, August 14th, 2024, between 14:22:07 UTC and 15:09:11 UTC, the DriveID identity platform emitted 7,312 vehicle-identity attestations carrying sig_counter = 0 — a value the issuer had not seen in production since the ephemeral-token branches were quarantined in Q1‑2022. The records passed upstream signature verification because the long-term-ledger boundary invariant was being bypassed on a fallback code path. The fallout was not detected by automated guards; it surfaced when twelve merchant tenants — clustered in dealer-financing and fleet-lease — began opening tickets against their Vehicle Trust Console dashboards, reporting that round-trip verification of freshly-issued attestations against their own internal vehicle-history ledgers had started failing with error class SIG_COUNTER_DESYNC. Every one of the 7,312 affected records was eventually revoked and re-issued with a corrected signature counter; no records remain in the broken state at the time of writing.

The proximate cause was a library version bump in the VIN canonicalisation stage, from vin-parsers@4.7.3 to vin-parsers@5.0.0, deployed on Monday, August 12nd, at 18:04:09 UTC as part of routine dependency hygiene under ticket DRDDEP-3827. vin-parsers is the canonical reference for WMI/VIS/VDS decoding against ISO 3779 and the U.S. NHTSA 2010 model-year position-10 standard. Version 5.0.0 introduced a stricter validator for the position-10 character class: it rejected the placeholder Z and the unassigned codes 0, 8, 9 (introduced for cross-manufacturer prototype vehicles in the 1995–2009 era) where 4.x had silently coerced them to CANONICAL_OK_WITH_FLAG { model_year_uncertain: true }. The new validation response from the library was INVALID_STRUCTURE — POSITION10_RESERVED.

In our pipeline, a canonicaliser result of INVALID_STRUCTURE is supposed to be a hard stop: vin-canonicalizer should respond to the merchant with a 422 Unprocessable Entity and never advance the request to the downstream attestation issuer. The bug, however, was that vin-canonicalizer is configured (per ADR‑0911, dated 2024‑02‑12) to translate any non-OK status into a JSON envelope compatible with the legacy attestation-issuer v3 contract, which expects the field vin_status: 'absent' | 'malformed' | 'valid'. The translation layer was reusing 'malformed' for INVALID_STRUCTURE and 'absent' for 'null', but in the v3 contract 'absent' is the explicit signal for "vehicle identity is genuinely unavailable — fall back to ephemeral VIN-less attestation mode" — which is the path added in PR #4291 for driveaway permits, tow-away authorisations, and other short-lived records where the VIN is intentionally not present at issuance.

In other words: the canonicaliser had begun to misclassify legacy-vehicle VINs as genuinely absent, where before they had been correctly classified as present-and-canonical. The attestation issuer, receiving vin_status: 'absent', took the ephemeral-fallback branch and emitted the attestation without enforcing the sig_counter > previous_counter invariant — because ephemeral attestations deliberately omit the signature counter (they are scoped to a single merchant session and never enter the long-term audit ledger). That invariant is normally enforced at the long-term-ledger boundary, not at the issue endpoint. The bug was that the issuer's ephemeral-fallback branch was emitting an attestation with the long-term-ledger flag set to true when the request included persist: true (a field added in PR #4127), but that path had been written assuming vin_status: 'absent' was an honest signal from the canonicaliser. Two assumptions, both reasonable in isolation, collided.

Single-fault conclusionif you only read one paragraph

The platform did not break because a library upgrade was bad; it broke because an upstream translation layer silently re-classified a validation rejection as a domain-level absence, and a downstream issuer's compatibility branch treated domain-level absence as an honest signal. Either fault alone would have been silently corrected by the other layer's guard. Both faults together produced a signed record that downstream consumers could not distinguish from a valid attestation.

Detection was late (28m 49s) because the failure was a value bug, not a shape bug: every affected record parsed, signed, returned 200 OK, and persisted into the long-term ledger with the correct shape and a plausible signature. The only thing wrong was a single counter that no automated test ever checked. The alert that eventually fired was a customer-facing one — twelve concurrent ticket filings against the trust console within a seventeen-minute window — not an internal guard.

Mechanism & Code Trail #mechanism

The two faults are best read top-down. Below is the literal change that vin-parsers 5.0.0 shipped, the literal envelope mapping in vin-canonicalizer, and the literal branch in attestation-issuer that accepted the misclassified signal. All three were stable in production for at least 14 months independently. They only compose into a bug when an upstream change crosses the trust boundary between them.

// vin-parsers 4.7.x — accepted position-10 with an uncertainty flag
pub fn validate_position_10(ch: char) -> Pos10Result {
    if let Some(year) = year_code_map().get(ch) {
        Pos10Result::Ok(year)
    } else if is_reserved_pre2010(ch) {
        // pre-2010 reserved codes (Z, 0, 8, 9)
        Pos10Result::OkWithFlag {
            year: Option::None,
            flag: ModelYearUncertainty::Certain,
        }
    } else {
        Pos10Result::InvalidStructure("POSITION10_NOT_A_YEAR")
    }
}

The 4.x release caught this exact same input class and carried it forward as a soft-uncertainty flag. The 5.x maintainer rationale (release notes § 3.1.2) is that "position 10 was reserved for unknown only during the transition window; anything not in the ISO‑3779:2010 table is now treated as malformed." Maintainer-side the change is defensible. On our side, the change is the trigger.

Composition patterntwo single-fault-prone components

This is a textbook compatibility shim coupled with an invariant missing-on-fallback. The shim was written so that the legacy contract would survive future canonicalizer semantics; the fallback was written so that ephemeral mode would survive merchant integration tests. Neither piece of code is wrong in isolation. Together they trusted each other's defaults more than they re-validated the inputs crossing the trust boundary.

Why Continuous Integration Did Not Catch It #why-ci

Our CI matrix on the identity-gateway monorepo runs a snapshot-fixture test for the canonicaliser stage on every PR. The fixture comprises 480 VINs drawn from DriveID production traffic between 2022‑02 and 2024‑07. The test checks that the canonicalised representation round-trips identically through a given parser version, and it cross-checks a single downstream property: the resulting legacy envelope's vin_status field. CI passed for the 5.0.0 upgrade PR (idgw#3827) at 14:42 UTC on 2024‑08‑12. The 480-VIN fixture missed the bug for the following four reasons, in order of severity.

  1. Fixture was historical, not adversarial. The 480 VINs were drawn from production traffic at times when reserved position-10 codes were statistically rare in our merchant mix. Many of our dealer-finance tenants had migrated their older fleets off DriveID by Q4‑2023. The fixture had a 1.46% share of pre-2010 vehicles, vs. 9.84% in the population that would flow through the system after the upgrade shipped.
  2. Fixture covered shape, not semantic invariants. The cross-stage assertion only verified that the envelope field vin_status took one of three values (valid / malformed / absent). There was no test that re-checked the resulting vin_status: "absent" against the originating canonicalizer status. The test treated absent and malformed as interchangeable at the snapshot layer, which is exactly the assumption the production bug relied on.
  3. The fallback path's invariant was guarded by a unit test, but on the wrong fixture. PR #4291 shipped with a unit test that exercised issue_with_fallback() using synthetic envelopes constructed by hand. None of those envelopes were produced by the real canonicalizer, so the test could not detect a misuse of the absent signal.
  4. The promotion invariant lived at the ledger boundary, not on the issue path. ledger::append_promoted() checks that sig_counter > ledger.tip.sig_counter — but only when the records enters the ledger with the flag long_term: true. The ephemeral promotion path (persist: true) sets long_term: true after the attestation was already signed with sig_counter = 0 — meaning the invariant check happens against the same zero value, not the previously-stored tip counter. The check passes because 0 > 0 is false; the closure of ledger.append() tags the record as promoted and returns ok.

test/fixtures/vin/legacy-historical.snapshot.json will be expanded to 1,200 VINs, with guaranteed coverage of all nine position-10 reserved codes and a population-distribution match against the live 2024-Q3 traffic. Detection Lag (MTTD): Why 28 minutes #detection-lag

Mean-time-to-detect for SEV‑2 events in DriveID averaged 9m 04s across Q2-2024 (n=14 events). The 28m 49s figure for this incident is a 3.2× regression against that mean. Three factors contributed, in descending order of weight.

1. Sentinel blind spot (≈ 11 minutes). The victory-research-sentinel service polls issuer.outbox every 60 seconds for shape anomalies and signature-verification failures. The fallback path emits signatures that verify; the sentinel saw a healthy stream. The sig_counter was not in the sentinel's verification payload. A counter-invariant sentinel was proposed in ADR‑1004 (2024‑05) and rejected at planning as "low-value" (i​2v: 1 quarter-eng-time per quarter in detections expected). That decision is being re-opened — see Action RM‑7.

2. Latent-detection decay (≈ 14 minutes). Because the fallback path's payload shape matched the validator's contract, no upstream signal existed for an upstream noise. The first indicator of trouble was downstream of the issuer: three of our largest ledger-archival tenants run daily cross-checks between their own vehicle-history ledgers and the attestations they've received. LithiaFleet's check fired first at 14:34:11 UTC, but their pipeline suppressed the warning because the underlying API call had returned 200 OK. The check was re-run at 14:48:31 when their credit decisioning dashboard flagged 3 vehicles with mismatched ledger timestamps and a human logged a ticket. By the time the ticket was filed, DriveTime MSA Holdings had independently filed #478225, and the ticket-burst detector fired.

3. Detection-channel mismatch (≈ 3 minutes). The ticket-burst detector runs on the customer-trust-console stream with a 10-minute window and a threshold of 8 tickets. Two of the first three tickets arrived inside a 90-second window but on different console queues (one via the dealer channel, one via the fleet-lease channel, one via the wholesale-auction channel). The detector was configured per-channel, not globally. The per-channel configuration was a deliberate signal-isolation choice made in 2023 to keep false positives low during the Q3-2023 dealer outage. The reverse isolation (no global aggregation) was not re-thought. See Action RM‑9.

Defense in depth gapnot the same as "no monitoring"

DriveID has forty-seven sentinels. None of them was wrong. The failure was that all 47 were exercising the same trust assumption (a valid signature means a valid issuance), and that assumption broke. Counter-monotonicity sentinels would have fired at 14:22:07; shape sentinels could not. The action items below specify both the new sentinel (RM‑7) and a structural fix that makes any single sentinel's failure less load-bearing (RM‑11).

Synthesis — what the chronology shows

Three phases are visible. Phase A (14:22→14:50) is the production of forged records without any internal-state alert: 28 minutes in which every affected record passed through shape and signature verification while carrying a monotonicity violation. Phase B (14:50→15:03) is alert → acknowledge → investigate → converge on root cause, totalling 13 minutes and dominated by the time to correlate 12 tenant tickets against the can/reject-reasons.lab delta (8 minutes). Phase C (15:03→15:09) is the rollback + drain: under 6 minutes of pod-level restart and outbox drain before the tip counter re-monotonised. The composition suggests two intervention points: a tighter counter-invariant sentinel would have compressed Phase A from 28m to under 60s; a more aggressive rollback decision threshold could shave Phase B by ~5 minutes without changing Phase C.

tenant-router · v3.18.4

Tenant-router experienced no internal failure during the window, but its duplicate-detection heuristic compared requests on request body only — the same VIN arriving twice from the same merchant on the same session produced identical traces, meaning the de-duplication silently passed forged counter values forward. Tenant-router is not the cause but is now a candidate for hardening (Action RM‑12): de-duplication must hash the full envelope shape including the signature counter hint, not just the body. Two requests received by tenant-router carry identical body but different signatures in the forged cluster (the issuer's fallback path used a nonce; in 2 of 7,312 cases the nonce collided with a prior cluster) — these collisions were not a correctness issue but they are visible in the audit log.
